## 实施沉淀

<!-- notes:begin -->
### 怎么实现

- **HTTP 入口**：新路由只做 `requireAdmin(ADMIN)` 与组合；GET/PATCH handler 在 `settings.ts`，PATCH 依次同源 → 120/min 限流 → 2KB 限体 → strict `{timezone, expectedVersion}` → 服务；GET 只接受空查询参数。响应固定 `cache-control: private, no-store`，错误走 `classifyThrown`（401/403/409/413/503）。
- **真实认证入口（R1）**：HTTP 测试用真 Auth.js `csrf` + `credentials` 往返登录拿会话 cookie，再调 route 导出；不传 gate、不 mock `requireAdmin`/composition。专用 schema `m5t4` 在测试 `before` 里按正常 `prisma db push` 应用完整 schema，`after` 按本次创建的用户 id 与 routeId 精确清理（含 `auth.login_success` 审计）。
- **单语句双读**：`readSettingsAndBacklog` 用一条 `WHERE key IN (...)` 同时读 `analytics.settings` 与 `analytics.recompute`，缺行是 null。要求单语句的原因是这两个 key 的读取入口没有事务隔离前提，不能保证同一快照；PostgreSQL RepeatableRead 事务里的两条 SELECT 本身可以共用快照（此前“RR 下两次 SELECT 必然不同快照”的表述不准确，已更正）。
- **共用待办分类**：`parseAnalyticsSettingsValue` / `parseRecomputeBacklogStrict` 做 strict 解析（坏 JSON、缺字段、多余字段、`status≠pending` 都是 `corrupt`）；`classifyRecomputeBacklog` 统一给出 `absent` / `unusable(corrupt|stale)` / `future_floor` / `planned`，只有 `planned` 带完整 expected 值。GET 与作业都调它：`planned` 才返回 `recomputableFrom(now, timezone)` 的读时 live，其余 null；settings 损坏仍 503；`floor == now` 属 planned。
- **重算窗口**：`rebuildFrom` 是日界 UTC 瞬时，先 `siteLocalDate` 映射成站点日；窗口 `[max(floorDate, earliestDate), currentDate]`，上界先定死不再枚举未来日；`floorDate < windowStart` 时只用 `skippedRange{from,to,dayCount}` 记录旧区间，不逐日、不填 0、不扩 13 月 raw；超 `maxBatchDays` 继续整组拒绝，不新增分页/推进。`skippedRange` 非空或 `skippedDates` 非空 → `partial`。
- **原子消费**：共享聚合作业在同一 RR 事务里先按完整六字段值 `DELETE … WHERE value = $expected::jsonb`（全值 CAS，不做 `->>`/`::int` 字段谓词），再 `complete` 写 JobState；`complete` 抛错整组回滚（含 DELETE）。CAS 0 行只记 `analytics.recompute_consume_miss`，不推断原因、不失败、不删别行；`absent/corrupt/stale/future/empty` 一律不调用消费。
- **不变量与失败**：预算/回滚/未知提交分开记录；`runWithDeadline` 的 503 只说明 HTTP 计时，不是提交未知的充分证据；受控用例只断言「提交已确认 / 提交前中止」两类，未知窗口不写成 PASS。
- **未越界**：不改 schema/契约定义/CI/生成器/retention/lease-repo/aggregate-repo；`contracts/analytics.ts` 只补字段注释；M3 composition 冻结，M5 树只加自己的 settings 接线。

### 踩坑

- **rebuildFrom 必须裁剪 floor 之前的迟到日**：首版把常规 48h 迟到日与新窗口做并集，P6（floor == now）把前两天的迟到日也带进本轮，窗口下界失效（13/14）。改为有 rebuildFrom 时只取 `[max(floor, earliest), currentDate]`，floor 之前的日既不重算也不能算进新 revision 的窗口；P6 转绿。
- **GET live 不能用行内存储值**：待办行里是 PATCH 时刻的起点，GET 必须用服务 `now` 重算 `recomputableFrom`；同一次读取里只读不改待办。
- **完整值 CAS 不能用字段谓词**：同 revision 的其它字段被外部改写时字段谓词仍会误删；strict 解析出的完整对象做 jsonb 等值匹配才安全，坏值到不了 DELETE。
- **超限分支不可达是设计**：生产窗口 ≤32 天，`maxBatchDays=500` 只为防御；不因此新增分页/推进，负控只证明“整组拒绝、无行、待办不动”。
- **真实登录会写登录审计**：`auth.login_success` 的 `actorId` 是测试用户 id；清理必须先按 actorId 删审计再删用户，否则用户级联走后留下孤儿审计行。R1 已按此收口并复核全表归零。
