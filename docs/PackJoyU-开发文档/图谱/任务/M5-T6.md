## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 通过HTTP以有效签名同意cookie分别发送page_view/product_view/model_view_start/model_load_success/model_load_failure/chat_start
逐项断言必填navigationId/viewId/productSlug、已发布产品白名单及strict长度边界。伪造/未发布产品、未知种类、超长字段、含敏感query的完整URL均拒绝，受拒事件行数不增加
每cookie第121个/分钟事件或IP-HMAC第301个/分钟事件按10节限流，429带Retry-After，受拒事件不落库
查询原始事件字段确认无原始IP、跨站指纹、email、聊天正文或敏感完整URL（[[E-47]]）。2) PostgreSQL重复eventId/semanticKey同载荷仅一行，异载荷409
同viewId success/failure只能一种终态，产品页事件与start/terminal分开存，failure不写success
-48h/+5min之外拒绝。3) 撤回cookie后请求403且事件行数不变
客户端模型生产者由M2-T7接入，浏览器同意及普通页面生产者由M5-T7接入。

## 实施沉淀

<!-- notes:begin -->
已发布产品是 `Model3D.productSlug`，条件为 `published` 且 `status=READY`。静态产品清单和品类 SEO slug 不参与准入。`page_view` 没有产品字段。`chat_start` 的 `productSlug` 可选，不进入 `semanticKey`；一旦出现，仍须已发布。同一 `navigationId` 再带上不同 slug 是另一份载荷，返回 409，不另起一行。

带查询串的路径必须整条拒绝。共享站点路径 schema 会去掉 `?` 和 `#`。先解析再入库会接受这条事件，并把敏感查询从行里抹掉。

同一 `viewId` 的成功与失败共用语义键（浏览器哈希、`model_terminal`、`viewId`）。后到的另一种终态是 409，第一行的 `kind` 与 `failureReason` 保持不变。失败不会写成成功。`product_view` 和 `model_view_start` 用各自的键，与终态分行存放。没有先到的 start 时，终态仍单独入库；聚合不在本任务。

时间窗在去重之前。窗外重放是 400 `event_time_out_of_range`，不是重复。一批里任一条非法、未发布、含敏感路径或越界，整批不落库。409 回滚整批，包括同批里本可新增的行。同载荷重复可以和新增混在一个 200 回执里：`acceptedIds` 与 `duplicateIds`。

限流按事件条数。一批放不下时，把本请求已经加上的次数从 cookie 桶和 IP 桶退回，含那一次溢出的递增，因此第 121 条和第 301 条仍是精确边界。同源失败和同意失败不占事件配额。非法 JSON 和超限正文占 1 条。存储错误按关闭处理。IP 只用来派生限流键，不进入仓储。

没有撤回名单。浏览器不再附带有效 `pj_analytics` 时请求为 403。未过期的旧签名 cookie 仍然验得过。

载荷哈希用同意密钥再套一层标签 `analytics-event-payload-v1`。`deploy.sh` 里现有的 `prisma db push` 会创建本表，脚本未改。上线前仍要走该流程。
