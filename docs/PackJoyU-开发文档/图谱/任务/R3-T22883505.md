## 实施沉淀

<!-- notes:begin -->
精确 head 的冻结安装和 `pnpm build` 由本 PR 的 GitHub Actions 证明：`build-and-audit` 要求 `.next/standalone/server.js` 非空，并且 `STANDALONE_TEST=1` 的 TAP 是 skipped 0。本机 WSL Ubuntu 20.04 只做预检。本机 Postgres 是 12.22，CI 的 e2e 数据库是 Postgres 17。Playwright 1.64 在 ubuntu20.04 上拒绝安装自带 Chromium，所以本机只在 `E2E_BROWSER_CHANNEL=chrome` 时改用已安装的 Google Chrome。CI 不设这个变量，继续用自带 Chromium。

`STANDALONE_TEST` 没设置时，三例启动检查跳过，普通 `pnpm test` 不必先构建。设为 1 时，缺 `server.js` 必须失败。Node 的测试运行器在全部跳过时仍会退出 0，CI 因此核对 TAP 的 `# skipped 0`。

`getuid()===0` 时，上传目录检查不做 `chmod 0500` 那一截。这是用例内部的分支，TAP 的 skipped 仍是 0。CI runner 不是 root，存在和不可写两截都会执行。root 上的 0500 不能当成目录不可写的证明。

冒烟进程不要设 `APP_ENV=production`。localhost 地址过不了生产环境检查。启动检查自己使用 `APP_ENV=production` 和假的公开网址，那是另一条路径。构建时必须带上 `NEXT_PUBLIC_ADMIN_API=http`。没有它，后台页面使用示例数据，不会发出 `GET /api/admin/inquiries`。

Playwright 1.64 拒绝在 `describe` 里写 trace、channel 和 launchOptions，所以这三项在文件级 `test.use`。`e2e/brand-smoke.spec.ts` 里的每个测试都会录 trace。其他 e2e 文件仍用 `playwright.config.ts` 的 `retain-on-failure`。该配置已经用 `node .next/standalone/server.js` 起服务，缺产物时直接抛错。`e2e/global-setup.ts` 已经在有 `DATABASE_URL` 时播种管理员。这两处保持不动。

Windows 盘（drvfs）上启动 standalone 会超过 30 秒时限。把 `.next/standalone` 拷到 ext4 再链回项目，只影响本机启动时间，不进入提交。把整份 `.next` 移出项目目录后，Next 按真实路径解析，找不到 `@prisma/client` 和 `sharp`。加长 30 秒时限盖不住这种慢盘，也会把慢盘写成通过。

Web Vitals 在文档卸载时才 `POST /api/rum`。站内点击不卸载文档。目录页之后要再做一次整页进入 `/en`，才等得到 204。

后台没有登录页。会话只来自 `POST /api/auth/callback/credentials` 写入的 Cookie。不写 localStorage 或 sessionStorage。同一次运行只登录一次。同一 30 秒窗口里重复使用当前 TOTP 会失败，所以每次使用一个新的合成邮箱。

密度只量七个已实现工作面的两个视口，共十四次。参数是 density 7、gutter 16、gap 16、pad 16，主区域是 `main.adm-main`。正式结果是精确 head 8ec1dd4 的 GitHub Actions run 39897468015（`node .next/standalone/server.js`，Postgres 17，Playwright Chromium）：六次通过、八次失败。通过包含询盘 1920x1080 work，D1–D6 与 overflow 都是 pass，fill 0.971，leftGap 25。八次失败记在本批 `admin-density-applicable-failures` 围栏里。本机空库测量只留在证据的 localPrecheck。判定函数和后台样式都不改。样品申请、内容、数据看板保持禁用。`/admin/samples`、`/admin/content`、`/admin/stats`、`/admin/mail/unassigned` 仍返回 404。`build_docs.py --batches` 才会按围栏生成返工任务；围栏留在 verdict 为 open 的记录里，原收口结论不改成 clean 或 fixed。
