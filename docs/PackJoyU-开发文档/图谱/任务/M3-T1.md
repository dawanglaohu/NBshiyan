## 必须处理的边界

- [[E-01]]　会话持久化与记住设备期限
    - 触发：未选“记住此设备”
    - 期望：保留当前 2 小时会刷新的会话策略，不误写成固定 2 小时强制退出；选中后连续活跃也不能突破从签发起算的 30 天绝对上限。
- [[E-02]]　会话持久化与记住设备期限
    - 触发：已记住的设备超过 7 天无有效服务端活动
    - 期望：下次受保护请求要求重新验证，刷新 JWT 不能复活已过期会话。
- [[E-03]]　会话持久化与记住设备期限
    - 触发：改密、重置验证器、禁用账号或执行“退出所有设备”
    - 期望：服务端撤销该账号旧凭证，旧 JWT 即使尚未到期也被拒绝；普通“退出”至少撤销当前设备会话并清除本地登录状态。
- [[E-69]]　设备会话与Auth.js期限接合
    - 触发：普通会话距上次有效活动达到 2 小时，或记住设备达到 7 天闲置/首次签发起 30 天绝对期限中的任一项
    - 期望：服务端拒绝授权并清理可写响应中的 cookie；JWT 和 Set-Cookie 到期时间均不得越过该设备实际允许期限，刷新不能延长绝对上限。
- [[E-70]]　设备会话与Auth.js期限接合
    - 触发：cookie/JWT 仍有效，但设备已撤销、账号禁用、凭证版本变化或服务端校验不可用
    - 期望：受保护请求不得仅凭 cookie 放行；在请求范围内去重查询不能演变成跨请求忽略撤销的缓存。

## 实施沉淀

<!-- notes:begin -->
普通会话的 `absoluteExpiresAt` 为空，有效期从 `lastActivityAt` 滑动 2 小时；记住设备受 7 天闲置和签发后 30 天绝对期限共同限制。Auth.js 的 encode 将 JWT exp 收到设备截止前一整秒，响应适配将 Set-Cookie 的期限收在该 exp 内。读取 session 和 account 不更新活动时间，不能靠读取复活过期或撤销设备。

API 守卫从请求 cookie 解密 sid/sv 并重读当前 User 与设备；SSR 通过 Auth.js 后也执行同一规则。账号有效之后先查设备归属、版本、撤销和期限，最后才判请求路由的角色。无效设备是 401 并清理可写 cookie；有效设备的角色不足是 403，保留会话。

Auth.js 与 API 只读取当前环境选定的同一 cookie 名称和解密 salt：生产模式使用 `__Secure-authjs.session-token`，开发模式使用 `authjs.session-token`。即使请求同时带两种 cookie，也不回退读取另一个命名空间，避免 API 与 SSR 识别为不同账号。

清除会话同时发送 `Max-Age=0` 与过去的 `Expires`，可写 cookie jar 也设置 `expires: new Date(0)`。当前 Next cookie 解析和 mutable-cookie 合并可能不序列化数值为 0 的 maxAge；过去日期使最终响应仍明确删除 cookie。回归直接运行实际 Next 解析与合并链，并检查合并后的 expires，不把响应头正则命中当作浏览器删除成功。

账号改密、角色、启用、解锁或重置验证器的写入返回已提交的 `sessionVersion`。五处撤销调用只标记比该版本旧的设备，新版本真实登录在撤销调用之前完成也保留。首次绑定确认仅增加 User 的会话版本，旧设备版本在下一次请求仍会被拒绝。

普通 Auth.js signOut 先提交当前设备撤销，再交出清 cookie 的响应；撤销失败返回 503。`publicUser` 保持原列表字段，完整 AccountDTO 和 `passwordlessEnabled` 由 GET account 提供。路由仅导出合法 GET/runtime，响应工厂置于服务器模块，真实鉴权和所有最终结果均经过 T14 计数。
