# M3-T4　签发管理员目标恢复permit

- 所属模块：[[M3]]　后台访问与账号：负责统一后台登录页和后台公共外壳、个人设置、设备会话、验证器绑定与登录方式切换、会话撤销及独立受限恢复，并负责既有后台页面的共享视觉迁移/回归；不改其询盘/邮件/规格/模型业务，消费 M1 的唯一视觉 token。
- 前置依赖：[[M3-T3]]、[[M3-T1]]
- 完成后解锁：[[M3-T9]]、[[M3-T18]]、[[M3-T19]]

## 输入 / 产出

- **输入**：M3-T3目标新鲜授权与当前权限；09/10 permit15min和审计协议。
- **产出**：AdminRecoveryPermit；POST /api/admin/account/recovery-authorizations及POST /api/admin/users/[id]/reset-2fa兼容别名。

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 调用方/接线点：真实ADMIN handler→recovery-authorizations
当前密码+新TOTP取得绑定他人的RECOVERY_AUTHORIZE grant后签15min permit，target不可自己
旧无body直接reset、仅session、访客邮件请求、SALES/EDITOR均拒绝且目标因素不变（[[E-13]]）。2) permit随机256bit、仅存hash/一次响应，授权核销/target/source/reason审计同事务，重复同grant不再签发
日志无permit明文，响应丢失不自动签第二份
普通passwordless会话不能借此省略现密码（[[E-73]]、[[E-75]]）。

## 必须处理的边界

- [[E-13]]　C-04 验证器丢失与单管理员恢复
    - 触发：另一管理员代为授权恢复
    - 期望：授权方必须重新验证，不能仅凭已打开后台页面或访客邮件请求重置其他账号。
- [[E-73]]　敏感设置的新鲜本人验证
    - 触发：两次请求并发使用同一 ActionGrant，或把改密码授权用于关闭验证器
    - 期望：在敏感变更事务内按动作、设备、账号及凭证版本校验并一次性消费授权，只有一个匹配请求成功，目的不符请求拒绝且不能执行变更。
- [[E-75]]　敏感设置的新鲜本人验证
    - 触发：用户忘记现密码但仍能使用启用后的无密码登录
    - 期望：把“D3”指向09/10节已定义受限恢复路径和一次性 permit/restricted cookie；普通无密码登录不改，敏感设置缺当前密码时不得签发普通 ActionGrant，仅凭已登录会话或一枚TOTP的直接请求拒绝并无变更，受限恢复只可新绑定且审计。

## 实施沉淀

<!-- notes:begin -->
- permit 只授权「目标账号重新绑定新验证器」，不替目标改任何因素、不递增 sv、不撤销设备、不开后台会话。放行点在 M3-T19 的 recovery/start：它按 permit 绑定时的 sessionVersion 做 CAS 核销，sv 变化即失效。因此这里不能顺手做 reset2faData / revokeUserDevices，否则恢复中断会先毁掉原有效绑定。
- 新鲜验证不在这个入口重做。RECOVERY_AUTHORIZE grant 已由 M3-T3 的 reauth 用「当前密码 + 未用 TOTP」签发，本入口只认 grant，body 里不接 password/totp：普通 passwordless 会话缺现密码时拿不到 grant，也就签不出 permit（E-75）。授权方 User 行由 grant 的 consumeLocked 在同一事务里按 User→Device→Grant 上锁，所以这里对授权方/目标都只补读，不再 FOR UPDATE——两个管理员互为目标时若各自抢锁会交叉死锁。
- 审计必须和核销同事务。旧 audit() 走全局 prisma 且吞掉写失败，会产生「permit 已发、审计没记」的假成功；因此加了 auditInTx(tx)，失败随事务回滚。meta 不含 token、邮箱、验证码。
- 两个入口共用同一 handler，只是目标 id 来源不同（body 的 targetUserId 或 URL 的 id），避免别名分叉出第二套校验。随机 token 用 randomBytes(32).toString('base64url')，与 M3-T3 的 grant token 同形状，DB 只存 sha256 hex。
- schema 只加 AdminRecoveryPermit 与共享 RecoverySource 枚举；AdminRecoverySession、consumedAt 的 CAS 核销、pendingPasswordHash 的本地 TTY 预授权都留给 M3-T19 / M3-T18，不在本任务提前写死，保证后继能复用同一数据层。
- 已知冲突：#347 的存量测试（admin-reset-2fa-unlock-347 / admin-enroll-token-347 / admin-enroll-hardening-347-348）与 UsersAdmin.tsx 仍焊死旧「无验证直清 TOTP + 发 enrollLink」形状，与本任务验收标准 1（E-13 拒绝旧旁路）不可两全。它们不在 M3-T4 有效路径内，UI 迁移按契约归 M3-T9；本 PR 不擅自改，需后续窗口定点适配，否则全量单测会红。
- Windows 本机 pnpm 11 与锁文件 overrides 不匹配，按 17 节用 npx pnpm@10.34.6 冻结安装；prisma validate 需要临时假 DATABASE_URL（schema 本身已通过 generate）。本机无 PostgreSQL，新 http 测试默认 skip，CI 用 M3T3_TEST_DATABASE_URL 专用库必跑。
