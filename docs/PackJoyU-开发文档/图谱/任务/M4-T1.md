# M4-T1　原子保存咨询首消息及唯一通知出箱

- 所属模块：[[M4]]　第一方人工咨询：负责访客必要会话、人工消息与离线留言、ADMIN/SALES 收件箱和回复、未读、失败草稿与幂等重试，并保存真实收件和通知结果。
- 前置依赖：[[M4-T8]]、[[M5-T1]]、[[M5-T8]]
- 完成后解锁：[[M4-T2]]、[[M4-T4]]、[[M4-T10]]

## 输入 / 产出

- **输入**：M4-T8真实必要cookie、M5作业基础、09/10消息/会话/出箱约束。
- **产出**：ChatConversation/Message/ReadCursor/Notification schema；POST /api/chat/conversations及持久首消息服务。

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 调用方/接线点：真实POST conversations→cookie范围服务→会话+首消息+seq+messageId唯一出箱同事务，成功才返持久不变id/seq/receivedAt
数据库失败无部分记录，同UUID同payload返回原结果、异payload409、并发仅一消息一通知（[[E-18]]、[[E-31]]、[[E-90]]）。2) 16KiB限体后strict schema，正文1..4000code points纯文本，email省略/空值可发送，trim后超254、CRLF/显示名/非法格式字段错误
身份取cookie，不能关联他人session，拒分析仍接收且不建分析身份（[[E-39]]、[[E-40]]）。

## 必须处理的边界

- [[E-18]]　在线聊天实现路线
    - 触发：同一消息因重试重复提交
    - 期望：按客户端消息标识去重，收件箱只出现一条，不重复触发通知。
- [[E-31]]　C-01 人工聊天收件与回复入口
    - 触发：访客提交消息且服务端持久化成功
    - 期望：返回稳定的会话与消息标识并显示“已接收”，运营收件箱能读取；数据库写入失败则保留待重试，不显示已接收或客服已读。
- [[E-39]]　C-02 离线留言与发送失败恢复
    - 触发：访客主动提供空邮箱、非法格式或超长联系方式
    - 期望：镜像10节已定字段：email 可省略；填写时 trim 后≤254、单个合法邮箱、不接收显示名/CRLF；空值按不填处理，非法或过长返回字段错误并保留当前标签页原消息，不升级为已验证身份或投递保证。
- [[E-40]]　C-02 离线留言与发送失败恢复
    - 触发：访客拒绝分析但主动打开第一方人工聊天
    - 期望：允许完成必要咨询，不创建分析标识或加载第三方聊天脚本，聊天必要会话与分析同意分开处理。
- [[E-90]]　聊天通知持久队列
    - 触发：保存消息后进程立即中断，或客户端因超时重发同一消息
    - 期望：在同一数据库事务内保存消息及 messageId 唯一的出箱记录；已提交消息可在重启后继续通知，消息幂等命中不能新增第二条通知。

## 实施沉淀

<!-- notes:begin -->
四张表放在 `model ChatVisitorSession` **之前**：既有 `tests/chat-session.http.test.ts` 用 `schema.slice(indexOf('model ChatVisitorSession'))` 一直取到文件末尾来断言「没有 email 列」，把新模型追加在后面会让它把咨询表的 `email` 当成访客会话的列。这是本任务第一个踩到的坑，改顺序比改别人的测试安全。

幂等按 09/10 节定案：`createPayloadHash` 固定键序序列化全部七个入参（clientConversationId、clientMessageId、locale、bodyText、email、productSlug、sourcePath），缺省统一成 `null`，所以同键同载荷一定得到同一个哈希，同键异载荷返回 409 `idempotency_conflict` 并指到冲突字段。只哈希正文会漏掉 locale/email/productSlug/sourcePath 的差异，不够。

并发不靠进程内锁：两个唯一约束（访客会话 + 客户端会话 UUID、messageId 出箱）就是仲裁者。先到的提交，后到的撞 23505 后在**新事务**里重读并返回先到者的结果——在已中止的事务里继续查会拿到 25P02，必须换事务。

seq 用 `UPDATE "ChatConversation" SET "lastSeq" = "lastSeq" + 1 … RETURNING "lastSeq"` 一句完成取号，避免「先读后写」竞态；同一句顺带推进 `lastActivityAt` 与 `retainUntil`，通知重试和读标记都不碰它（E-86 只认成功保存的消息）。

四件套（会话、消息、seq、出箱）在同一事务里，任何一步失败整笔回滚。测试用一个在 `insertNotification` 抛错的 repo 替身验证回滚后四张表都是 0 行，而不是只证明代码里调用了 `$transaction`。

限流按 10 节「聊天写每会话 20 条/分钟」落在 cookie 桶；创建首消息也是一次写，所以和后续追加消息共用一个桶。顺序是先限体（16KiB）再解析再限流，超限体不占配额。

边界：出箱的真正消费属于 M4-T4；本任务只保证「消息提交即有一条 messageId 唯一的 QUEUED 记录」。`stableMessageId` 现在存的是 `messageId@chat.packjoyu`，发送时再包尖括号，重试复用同一个值。

**R1 返工（独审阻断项）**

限流补的是 10 节:121 的**新会话两桶**（cookie 10 次/10 分钟、可信边缘 IP 20 次/10 分钟），和 10 节"聊天写每会话 20 条/分钟"的写桶是两个配额，不能互相顶替。请求依次过 cookie 桶、IP 桶、写桶；IP 来自既有 `resolveClientIp`（只信 `X-Edge-Auth` + `CF-Connecting-IP`），key 里只出现派生后的 subject，不存原始 IP。测试用 `EDGE_AUTH_SECRET` + 每用例不同的可信 IP 隔离桶，不是关掉限流。

错误分类只认确定的类别：初始化失败/连接不可达/连接池超时（P1001/P1002/P1008/P1017/P2024）、事务超时 P2028、语句被 `statement_timeout` 取消（P2010 + SQLSTATE 57014）→ 503；触发器 `RAISE EXCEPTION`（SQLSTATE P0001）这类数据层错误仍是 500。分类函数没有复用 `designs.ts` 的 `isDbUnavailable`：那个模块在导入时就创建 Prisma 客户端，会让测试在设置 `DATABASE_URL` 之前就把全局连接钉死在错误地址上。

事务预算不是只加客户端 timeout。Prisma 的 `timeout` 只会在两条语句之间生效，已经在跑的慢语句会把事务拖到 7,080ms（实测）。现在事务开头 `SET LOCAL statement_timeout = 4500`、`lock_timeout = 4500`，客户端 `timeout` 用 5,000ms 兜底：语句在 4.5s 被服务端取消，留 0.5s 回滚与响应，同一用例返工后实测 4,698ms，且四表零增量、移除慢触发器后同键重试成功。

测试载体只读专属变量 `B9_M4T1_TEST_DATABASE_URL`（必须 loopback），**绝不回退通用 `DATABASE_URL`**；`CHAT_REQUIRE_DATABASE=true` 时缺专属 URL 直接抛错而不是 skip。schema 用随机名，先查 `pg_namespace` 确认不存在再 `CREATE SCHEMA`（无 `IF NOT EXISTS`），只在确认由本进程创建后清理；预存同名 schema 的负例证明不会被认领或删除。
**R2（Jev C：只读校验 → 事务内守卫与最终 touch）**

C3 的实现不是「先 resolve 再提交后 touch」：那样在提交与 touch 之间仍有窗口，也做不到失败不续期。现在 `resolve()` 只读校验并产出带品牌字段的 `ValidatedSession`，`createFirstMessage` 把它作为**必填**入参（没有默认 no-op）；事务第一步就按同一 tokenHash 做一次新鲜度守卫，而且这次守卫在 `readExisting` **之前**，所以幂等重放也绕不过去。写入或读到原结果之后，用同一个事务里的条件 `touchIfValid` 收尾：0 行 → 抛 `ChatSessionNoLongerValid` → 整笔回滚 → 401；1 行才 commit → 200。于是 400/409/500/503 都不会推进闲置期限，重放 200 会推进，bootstrap 仍走原来的 `establish()`。守卫与 touch 都取**调用时刻**的新时间，不拿事务开始时间当有效性判据；撤销 UPDATE 与 touch 在会话行上串行，但自然过期到 commit 之间仍有极窄时钟跨越，不宣称锁消除。

B2 的截止从「每条语句固定 4,500ms」改成**剩余预算**：事务内用 `performance.now()` 单调计时，每次可阻塞 SQL 前按 `5000 − elapsed − 800` 重设 `statement_timeout`/`lock_timeout`，小于 50ms 就直接放弃。arm 覆盖了守卫、`readExisting` 的两条 SELECT、Model3D 查询、会话插入、seq 分配、消息插入、通知插入与最终 touch——不是按仓储方法一次性设置。双 3.5s 触发器的累计场景由原来的 7,048ms 降到 4,423ms。客户端 `timeout` 保持 5,000ms 兜底（不放大），`maxWait` 2,000ms 属事务外排队、计入 HTTP 而不计入事务；commit/WAL 不在 `statement_timeout` 覆盖范围内，作为残留边界如实记录。

C1 的 IP 桶不再写原始 IP：key 用 `rateLimitKeyHash(rateLimitSubject(ip))` 派生，桶常量留在 `rules.ts`，服务端安全模块只在路由里用，不把 server-only 依赖带进共享规则文件。

测试侧另一个坑：测试文件静态导入 `composition` 会把 `db.ts` 在 `before` 之前加载，全局 Prisma 被钉在伪造的 `DATABASE_URL` 上，所有 HTTP 用例变 503；改为在用例内动态导入后恢复正常。<!-- notes:end -->
