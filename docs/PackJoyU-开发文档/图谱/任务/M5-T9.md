## 实施沉淀

<!-- notes:begin -->
站点日只用显式 IANA 和 `Intl`。不要用 `Date` 的本地 getter，也不要给本地日加 86400000 毫秒。秋令时重复的那一小时整段只属于开始日；次日午夜是右开端点。`browserTimezone` 参数存在是为了让调用方显式传入并被忽略，非法的查看者时区不能拿来补站点时区。

可重算起点是不早于 `now` 减 30 个绝对日的第一个本地午夜。横跨截止时刻的那一天不算。截止时刻正好落在本地午夜时，那一天算。

缺行的逻辑当前值是 version 0、UTC、`timezoneRevision` 1。`read` 不插入。相同的时区再提交不升 revision、不写审计、不写待办；缺行且时区仍是 UTC 时只插入这条初值。改到另一个合法时区时 version 和 `timezoneRevision` 各加一，`previousTimezone` 用当前逻辑时区，缺行就是 UTC。

角色在校验请求体之前从当前 `User` 行重读。非 ADMIN 不拿 `SiteSetting` 表锁，也不能借这次写入把缺行变成初值。坏 JSON 返回 `service_unavailable`，禁止用 UTC 初值覆盖。version 或 `timezoneRevision` 再加一会超过 2147483647 时拒绝且不写。

锁序是先锁 `User`，再 `SHARE ROW EXCLUSIVE` 锁整张 `SiteSetting`，再锁设置行。表锁和作业租约相同，是为了让缺行和并发插入也能串行。

待办是另一行 `SiteSetting`，键 `analytics.recompute`，下一次时区变更整行替换。不要把待办字段塞进 `analytics.settings`：计数器按五个字段严格解析，多字段会让该行不可读。审计动作 `analytics.timezone_change` 与设置行、待办行在同一事务。审计 meta 只有 `previousTimezone`、`timezone`、`timezoneRevision`、`recomputableFrom`。

这里不改 `AnalyticsEvent` 的时间，也不改已有聚合行。超过原始保留的日子保持原 timezone 标签。后续接线调用 `createAnalyticsSettingsService`，本层不注册路由。

写入 `timestamp` 列时用 ISO 字符串加 `timestamptz AT TIME ZONE 'UTC'`。会话 `TimeZone` 不是 UTC 时，把 `Date` 直接交给 `timestamp` 列会把墙上时间平移。
<!-- notes:end -->
