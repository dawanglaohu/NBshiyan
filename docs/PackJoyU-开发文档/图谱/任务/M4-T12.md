## 实施沉淀

<!-- notes:begin -->
### 怎么实现

- **注册而非重写**：既有 `mail-queue` 变成固定作业。`createMailQueueJob` 用同一 JobState 租约；旧 route 在 gate/Bearer 后调 `executeJobRequest`，GET/POST 共享租约与摘要；`deploy/cron.nbshiyan` 只加每分钟 POST，409 视为租约占用正常跳过。
- **预算与收尾**：budget deadline = HTTP 55s − 250ms = 54.75s；剩余 ≤1s 停止领取；终态写剩余 >750ms 走普通预算，否则走绝对窗口 `[54.75s, 56.75s)`，每轮 `closeUsed` 只允许一次（D 回退与终态写先到先用）；SMTP 晚于窗口返回则 `mail.close_skipped`，不写不计数。
- **attempt 与 CAS**：reserve 在同一事务里 increment 后读回 attempts/lockedUntil；终态是一条 `updateMany({id,status:'SENDING',attempts,redactedAt:null}, data)`，count=1 即已写；成功结果遇 stale 只追加一条 `FAILED+unknown_delivery+同attempt` 的条件 SQL 升级 SENT。失败 0 行不计数、不发配置告警、不延长保留期。
- **D 回退**：reserve 后、SMTP 前预算耗尽 → 同一收尾事务回 QUEUED + 原 deferredUntil，attempts/retryCount 保留、capDay/lockedUntil 清空；命中后立即 `break`，否则下一行会二次触发回退。
- **告警**：`sendAdminAlert` 返回 `'sent'|'skipped'|'failed'`，在同一 deadline 的入口、限流后、`sendMail` 前三处检查；队列在调用前再按 `deadlineAt − 500ms` 自查。`sendMail` true→sent、`mail_disabled`→skipped、抛错（含 `SMTP_CONFIG_*`）→failed，旧三参调用兼容。
- **交互路径**：直发/重试不传 budget/close；终态 0 行时按一次重读返回当前状态，已匿名化返回 409 `anonymized`，不套队列预算。

### B1 收尾分类（本轮返工）

- 仅按本次操作的结构化错误分类：`P2034` 或 `P2010`＋`meta.code ∈ {40001,40P01,57014,55P03}` → `close_rolled_back`；`P2028`、连接类、`PrismaClientUnknownRequestError`、未识别错误 → `close_unconfirmed`。
- 不再用 `!callbackDone` 或 `txStarted=false` 推断“已回滚/未发起事务”：已调用 `$transaction` 后、回调开始前也可能超时/断连；只有调用前的本地校验失败（如收尾窗不足）才是 `close_skipped`。内部 `stage` 字段被 `mailLog` 的 SAFE_KEYS 过滤，日志只可观测 `mail.close_rolled_back`/`mail.close_unconfirmed` 事件；不能以日志证明 callback/commit 阶段。
- 无库回归 B1-1..B1-19＋B1-8b（20 项）覆盖 terminal/D 回退 × callback/commit × 已知/未知 × 本地 skip/`$transaction` 前拒绝。

### P2-A 错误传播（本轮续接）

- `processMailQueue` 的 stale/due/recipient/dropped 四阶段非预算错误一律上抛并停止后续操作；预算分支保持原返回/break，不改成 503。
- `queue-job` 对非预算失败只尝试一次预算内失败登记：persisted/unpersisted 都传播原错误，由 `executeJobRequest` 映射 500 `job_failed`；budget 才走 timeout。失败登记未确认不宣称已写 FAILED、不重试。
- 失败摘要仍是 `EMPTY_COUNTS`，**不代表本轮没做过工作**；部分已确认终态可能未进入失败摘要。已提交早行/已发 SMTP 不撤回、不重发、不补计数；“下一分钟”指下一次正常调度按持久状态接管，不是自动重放本轮操作。
- 无库回归 P2-1..P2-8 覆盖四阶段停止、预算分支、失败登记成功/未确认、`createMailQueueJob→executeJobRequest→handler` 500、早行 SENT 保留。

### P2 真实 cron 与隔离 SMTP（本轮）

- **setup**（`local-smtp.mjs`）：在既有私有 mount/net/pid namespace 中，先校验 UID/GID>0（任何 mount/spool/crond 之前），再从 `/usr/bin /bin /usr/sbin /sbin` 取 `stat/install/busybox/setpriv/sleep` 并校验 uid=0 且 `mode&022==0`；`/tmp` tmpfs 后建 root-only `/tmp/mail-cron` 与 app-owned `/tmp/mail-cron-state`，安装 tick、写 tab 四字段 `run.conf` 与 `spool/root`，前台启动 busybox crond；随后 `exec setpriv` 降权。`CRON_SECRET` 只进 exec 注入环境。
- **tick**（`mail-cron-tick.sh`）：root 部分只读 root-only `run.conf`（无 source/eval），校验后 `exec setpriv`；node 部分先 `lstat armed`，再**原子 rename 消费同一 arm**（一次 arm 最多一次 POST），然后打开并验证日志 fd（`O_NOFOLLOW|O_NONBLOCK`，**无 O_TRUNC**，fstat 后 `ftruncate`）、secret 同法；日志状态写入已打开 fd。失败按 outcome 区分：`log_open_failed` **exit 3** 与 `secret_invalid`/`secret_empty` **exit 1** 都发生在 POST 前，未 POST；`posted:<status>` 表示已收到真实 HTTP 响应（请求已发出、状态已知），邮件效果按 route 与 status 判断，**不能因 exit 0 推断已投递**；**exit 0** 对应 `res.ok`(2xx) 或 409，**exit 1** 对应 401/503 等非 ok（401 未入队、503 邮件效果未知），两者都不写成“请求结果未知”；**exit 1** 且 `post_failed` 只证请求尝试未正常完成，可能连接前拒绝/DNS/TLS，也可能发送后超时，不能断言已发出或未 POST，邮件效果未知；**exit 4** 且 `log_write_failed` 只证响应已收到、状态日志未可靠保存，请求/邮件效果随对应 `posted` 状态，不能从该 outcome 补造丢失的 status。不得把 exit 1 一律当未 POST。
- **phase**（`mail-cron-phase.mjs`）：`exec --mode http-real` 调用以继承完整 env；校验 http-real 产物与九字段 provenance（sourceCommit/tree/buildMode/runtimeMode/buildId/manifestSha256/verifiedFiles），不重复 activate；due 集合先断言为空；seed QUEUED `daily_cap_deferred`；应用 stop/重启后仍 QUEUED；arm 后由真实 crond POST，断言 SENT attempts=1、JobState SUCCEEDED `summary.counts.sent=1`、锁释放、sink received +1；N1 401 无 marker、N2 secret symlink→`secret_invalid`、N4 log symlink→`log_open_failed` 且目标不存在、N3 app uid 对 root 文件 EACCES/EPERM。
- **负控证据**：每次窗口要求新的 `last-attempt.at`，不用旧文件；四窗口有界。F2 的 UID0 负控由 `positiveIds` 共享校验覆盖（self-check 断言 0/负/非整数拒绝），不写 state/env 假 UID。
- **busybox 供应（B1）**：`mail-evidence` 在 `pnpm install`/build/namespace 前，从 `archive.ubuntu.com` 取固定 `busybox-static 1:1.36.1-6ubuntu3.1` amd64（**1,008,874 B / SHA256 `944b2728…e0ed`**），先校验大小与 SHA256 再 `sudo dpkg -i`；随后断言 `dpkg -L busybox-static` 含 `/usr/bin/busybox`、`dpkg -S` 归属 busybox-static、该路径为 root 属主 0755 普通文件、与 deb 内二进制同 SHA（`dbac288c…6ac14`），`--list`/`crond --help`/版本横幅全部用 `$bb=/usr/bin/busybox` 绝对路径（与 `local-smtp` `pick()` 的 `/usr/bin` 首选一致），PATH 上另有同名 busybox 只报告不采用；动态 `busybox` 包、其他已装 provider、未受包管理的既有目标均显式 STOP，不隐式移除 provider、不强制覆盖、不改 PATH、不用解包覆盖绕开 dpkg。sha/size/归属/owner/mode/二进制 SHA/版本/applet/选项任一失败都在昂贵步骤前停，不回退其他调度器。版本与 SHA 取自 noble-updates main Packages，其 SHA256 由已验签的 InRelease 覆盖；本机仅 `dpkg-deb -x` 解包运行 `--list/--help`，未安装、未启动 crond。
- **残余**：root part 仍有宿主写能力，namespace 不是文件权限沙箱；`install/setpriv/sleep/stat` 的运行时行为仍留真实窗首检；祖先不可替换未逐级证明。

### 踩坑

- **Prisma 的 `undefined` 会静默省略条件**：`attempts: undefined` 等于没有这个守卫。终态写必须显式整数校验，缺 token 直接 fail closed；内存夹具对 undefined 的方向与 Prisma 相反，不能拿它证明安全。
- **旧 route 单测靠内存 Prisma**：接线后 route 会真的 claim/complete，内存夹具必须补最小 JobState/租约 SQL 语义，否则旧用例变 500。
- **测试环境 SMTP 配置**：`MAIL_FROM` 的域不能等于/后缀 REPLY_DOMAIN，否则 `smtpConfig` 返回 `bad_from`，队列直接零计数。
- **收尾窗只一次**：D 回退与终态写共用同一个 `closeUsed`；回退后不 `break` 就会在同一轮用掉第二次收尾机会。
