## 实施沉淀

<!-- notes:begin -->
- 计数必须是一条 `INSERT ... ON CONFLICT`：requestCount 每次加一，只有 500–599 才给 errorCount 加一。换成 Prisma upsert 后，两条最终响应同时到达时可能都走 create，其中一次失败或少加。写失败只记录错误类别，调用方的 status 和 body 原样返回；这段写入不能放进业务事务。
- `body` 只为了失败时原样交还。请求体、IP、账号和查询串不能成为 SQL 参数或日志字段。`analytics.settings` 的 `updatedBy` 可以是账号标识，设置读失败时不能把整段 JSON 写进警告。
- 没有 `analytics.settings` 行时用 UTC 和 revision 1。行存在但形状或时区不合法时按计数失败处理，不能改记到 UTC，否则同一次请求会落入另一个 revision。站点日取该 IANA 时区的 `formatToParts`；机器时区，以及 `toISOString()` 的日期前缀，都不能代替非 UTC 的自然日。
- routeId 只接受第 10 节新 API 的「方法 + 模板路径」。Auth.js `/api/auth/[...nextauth]` 和既有 mail-queue 不在名单里，它们的信封仍按原协议。没通过白名单的字符串可能带着邮箱或 query，警告里不能留下原文。
- 配置错误只拼「字段 未设置/无效」。Zod 的 `issue.message` 会重复收到的值，秘密会跟着出去。`prodEnvProblems` 只追加策略解析结果，避免改动既有的精确问题列表；生产缺秘密由 `loadServerConfig` 拒绝，instrumentation 在原有启动检查之后调用它。这些名字本来就由那次检查要求。冻结对象不保存秘密副本，第一次成功之后不再读环境。
- 新错误体是 `{error,requestId,fieldErrors?}`。已经构造好的 Response，以及严格只有 `{error}` 的旧守卫体，保持原样。未知异常变成 `internal_error`，日志只留符合名称形状的错误类别。未通过 FieldErrorSchema 的字段错误整段丢掉。
- `createHttpServices` 供后续路由调用。本卡没有 GET `/api/admin/account`；那条响应的生产计数由 M3-T1 在最终响应处调用 `recordFinalResponse`。13 个月保留不是这张表自己的删除，清理作业也不能从这里导入。
