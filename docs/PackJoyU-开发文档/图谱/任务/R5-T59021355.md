# R5-T59021355　普通登录拒绝非空恢复码且不建设备会话

## 输入 / 产出

- **输入**：M3-T2 与 E-96 要求未知 mode、未由本人开启的 totp、普通 Credentials 带非空 recoveryCode 都走同一通用 Auth.js 失败，不签后台会话，响应不区分账号是否存在。src/lib/server/admin/login.ts:178 在 mode 分支前看到非空 recoveryCode 就返回 authorizeRecovery。authorizeRecovery 在 :214 以 recovery_code 完成登录。src/auth.ts:88 到 :91 在用户非空时 devices.open。src/lib/contracts/account.ts:35 允许恢复码代替验证码。tests/admin-login-mode.db.test.ts:342 期望未使用的恢复码登录成功且 deviceCount 为 1，:356 期望 totpLastStep 仍为空。:215 只覆盖非法短码 abcd1234。M3-T19 的标题是把恢复码或 permit 核销成受限会话，不是本条日常 Credentials。另一位 ADMIN 的 reset-2fa 存在且安全，但盖不住所有 ADMIN 都丢验证器的情况，因此仍须等 M3-T19 上线。等 #487 合入后再派，派单时按新 main 重标行号。
- **产出**：普通 Credentials 上的非空 recoveryCode 改为与未知账号相同的失败，不核销恢复码，不 open 设备。更新 tests/admin-login-mode.db.test.ts 中把该成功登录锁成期望的用例。不在本任务实现 M3-T19 的受限重绑入口
- **有效路径**：`src/lib/server/admin/login.ts`、`src/auth.ts`、`src/lib/contracts/account.ts`、`tests/admin-login-mode.db.test.ts`

## 验收标准

1) 已绑定账号使用当前密码加未使用的 10 位十六进制恢复码调用普通 Credentials 时，结果与未知账号相同，为 CredentialsSignin，AdminDeviceSession 行数不变，该恢复码哈希仍在，totpLastStep 不变。2) 同时附带 6 位验证码也不改变第 1 条。3) 不带 recoveryCode 的 password 模式与已开启的 totp 模式仍可登录。4) 未知 mode、未开启 totp、短码 abcd1234 仍是同一通用失败且无设备行。5) tests/admin-login-mode.db.test.ts 在修复前会因仍期望恢复码登录成功而失败，修复后通过。6) 不把本任务做成 M3-T19 的受限会话，不新增后台 e2e 登录。7) 派发前 main 上已有 /api/auth-admin/recovery/start，且至少 2 个 ADMIN 已开启 2FA。等 #487 合入后再派，派单时按新 main 重标行号。

## 实施沉淀

<!-- notes:begin -->
- 修复落点只在 login.ts 的 authorizeLogin：非空 recovery 一律走 genericCredentialFailure（与未知账号同路径，不查目标账号、不核销恢复码、不建设备）。`contracts/account.ts` 保留 recoveryCode 字段——`contracts-foundation.test.ts` 大量断言它仍可 parse（10 位 hex、连字符归一化、空串→undefined），删掉会连带红且属契约既有行为；`auth.ts` 也不用改，带 recovery 的请求仍经 credentialsFromRaw 进 authorize，由 login 层拒绝。任务卡虽列 4 个有效路径，实际只需改 login.ts。
- 删掉 authorizeRecovery 函数与 TODO(M3-T19) 字面，不只是让它返回 null：留着「TODO 说尚未移除」会与已兑现的事实矛盾，且生产文件里留 `TODO` 会命中审查的反造假扫描。`consumeRecoveryCode` 仍被 checkSecondFactor（reauth / 2fa-reset 旧路径）调用，保留不动；受限恢复的核销在 recovery-start.ts / recovery-repo.ts，与本任务独立。
- 两条存量测试断言为什么必须改（裁定 B，只在断言层、不放宽判据、不删不跳过用例）：① `admin-enroll-hardening-347-348.test.ts:195` 静态断言 login.ts 必须含那行 TODO——本任务正是移除它，保留会自相矛盾，故改为守卫式「authorizeRecovery 已移除 + 非空 recovery 走 genericCredentialFailure」，强度不降；② `admin-login-challenge.test.ts` 把「无 2FA + 非空 recoveryCode」期望从 totp_setup_required 改为通用 CredentialsSignin——旧期望会泄露「账号存在但未绑定 2FA」，违反 E-96「响应不区分账号是否存在」，且恢复码本不该再触发 totp_setup_required。其余两形态（无 2FA 纯密码/带 totp）仍断言 totp_setup_required，未动。
- `tests/admin-login-mode.db.test.ts` 的 5 条旧用例（期望恢复码登录成功/核销/锁定/并发一次）按验收 5 整体翻转为「通用失败、恢复码哈希仍在、无设备行、failedLogins/totpLastStep/sv/passwordlessEnabled 不变」，并补验收 1（当前密码+合法码）、验收 2（同时带 6 位码）、验收 3（password 模式与 totp 模式仍可登录）的具名断言。本机无 PostgreSQL，这些 DB 用例默认 skip、CI 用 M3T3_TEST_DATABASE_URL 专用库必跑，不冒充已跑并发锁证据。
