# M3-T19　原子核销恢复码或permit为受限会话

- 所属模块：[[M3]]　后台访问与账号：负责统一后台登录页和后台公共外壳、个人设置、设备会话、验证器绑定与登录方式切换、会话撤销及独立受限恢复，并负责既有后台页面的共享视觉迁移/回归；不改其询盘/邮件/规格/模型业务，消费 M1 的唯一视觉 token。
- 前置依赖：[[M3-T4]]、[[M3-T1]]
- 完成后解锁：[[M3-T5]]

## 输入 / 产出

- **输入**：M3-T4 permit与M3-T1设备撤销；现有恢复码hash；09/10 start锁序。
- **产出**：AdminRecoverySession；POST /api/auth-admin/recovery/start与受限HttpOnly cookie。

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 调用方/接线点：真实POST start→User锁后重读当前recoveryCodes/permit→核销+sv递增+旧sid/旧恢复会话撤销+10min restricted session+审计同事务
同码并发仅一次，不同码并发也不复活已用码
email单独/旧凭据拒绝（[[E-10]]、[[E-11]]）。2) 受限cookie仅Path=/api/auth-admin/recovery、Secure/HttpOnly/SameSite=Strict，不能请求后台、换Auth.js session或带ADMIN角色
原有效TOTP/password/defaultMode保持，中断/过期无新因素提交
SERVER_OWNER permit的预授权hash仅服务器事务转入session，HTTP body不接（[[E-14]]）。

## 必须处理的边界

- [[E-10]]　C-04 验证器丢失与单管理员恢复
    - 触发：正常登录
    - 期望：不显示为必填恢复码，单独“无法使用验证器”进入恢复流程；仅填写账号或邮箱不能获得重置权限。
- [[E-11]]　C-04 验证器丢失与单管理员恢复
    - 触发：使用账号与有效一次性恢复码
    - 期望：原子核销恢复码并签发受限、短时重绑定凭据，只能绑定新验证器，正确验证新码前不能获得完整后台权限；同一恢复码并发使用仅一次成功。
- [[E-14]]　C-04 验证器丢失与单管理员恢复
    - 触发：恢复中断或重置凭据过期
    - 期望：明确 restricted 凭据访问受保护后台必须拒绝；中断或过期不提交待绑定新因素，原有效绑定保持；持有效 restricted cookie 可重入同一 enroll，失效则按10节已定义恢复码/授权路径重启，不能换取完整后台会话。

## 实施沉淀

<!-- notes:begin -->
- start 只授权「开始一次受限重绑」，不发布任何新因素。递增 sv 会撤销旧设备，但 totpSecret/passwordHash/passwordlessEnabled/recoveryCodes 里未用的码都原样保留；恢复中断或过期不会把账号锁死，原因素仍可正常登录（E-14）。新 TOTP 的原子发布在 M3-T5 的 confirm，不在本任务提前做。
- 恢复码并发的坑在 09 节第 6 条：早期实现读旧 User 快照再整组覆盖 `[A,B,C]`，不同码并发重写会把已用 A 复活。这里先 `SELECT ... FOR UPDATE` 锁 User 行，再对**当前数组里恰好匹配的 hash** 做 `array_remove`，条件带 `${hash} = ANY("recoveryCodes")`，写失败整事务回滚，不留半核销。permit 同理用 `consumedAt IS NULL AND expiresAt > now AND sessionVersion = 当前` 的条件 UPDATE，同凭据并发最多一次成功。
- 锁序固定 User→Device→Grant。start 是登录前公开入口，不消费 `RECOVERY_AUTHORIZE` grant（那是 M3-T4 签发 permit 时的事），两条凭据族独立：`action-grant.ts` 明确不接受恢复码/受限 cookie。别把 start 接到 reauth 的 grant 核销上。
- 受限 cookie 与 Auth.js 会话彻底隔离：不同名（`pj_recovery` vs `authjs.session-token`/`__Secure-` 前缀）、Path 限定 `/api/auth-admin/recovery`（浏览器不会把它发到 `/api/admin/*`）、SameSite=Strict、HttpOnly、Secure、无 Domain。`recovery/start` 及后续 enroll/confirm 仍各自做精确 Origin 检查。`Secure` 无条件带上，沿用仓库 LoginChallenge cookie 的一致做法，本机 localhost/CI 不受影响。
- `SERVER_OWNER` permit 的 `pendingPasswordHash` 只在服务器事务里从 permit 转入受限 session，HTTP body 永不接该字段；`RecoveryStartRequestSchema` 是 strict 的判别联合（RECOVERY_CODE/PERMIT），多传 password/newPassword/passwordHash 一律 400 invalid（E-14、09 节第 10 条）。
- 重入语义：再次 start 会撤销该账号上一枚未完成的受限会话（`revokeOldRecoverySessions`），只留当前一枚有效，不会让两个受限 cookie 同时能走 enroll。cookie 里的 token 只进 hash，日志/审计/meta 都不含明文。
- 复用边界：M3-T4 留下的 `hashRecoveryPermitToken`、`createRecoveryRepo()`（接显式 tx、只读不抢锁）、`auditInTx`（本任务用 repo.createAudit 同事务版）、`RecoveryStartRequestSchema`/`RecoveryStateDTOSchema`、`restrictedTtlMs` 都直接沿用，没有另造第二套类型或 repo。`RecoverySessionSource` 比 permit 的 `RecoverySource` 多两个值，按 09 节分开设枚举，不合并。
- `AdminRecoverySession` 的 `pendingSecretEncrypted`/`pendingUntil`/`failedAttempts` 等字段按 09 节一次建齐，但本任务不写、不旋转；M3-T5 的 enroll/confirm 与 M3-T20 的本人换验证器才能消费它们，避免后继再改表。
- 本机无 PostgreSQL，`tests/admin-recovery-start.db.test.ts` 默认 skip；CI 用 M3T3_TEST_DATABASE_URL 专用库必跑，本机不冒充已跑 PG 并发锁证据。pnpm 11 与锁文件 overrides 不匹配，按 17 节用 npx pnpm@10.34.6 冻结安装；`prisma generate` 后 tsc 才认得 `adminRecoverySession`/`adminRecoveryPermit`。
