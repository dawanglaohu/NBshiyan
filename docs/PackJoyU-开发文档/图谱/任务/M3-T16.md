# M3-T16　原子切换本人登录方式与密码

- 所属模块：[[M3]]　后台访问与账号：负责统一后台登录页和后台公共外壳、个人设置、设备会话、验证器绑定与登录方式切换、会话撤销及独立受限恢复，并负责既有后台页面的共享视觉迁移/回归；不改其询盘/邮件/规格/模型业务，消费 M1 的唯一视觉 token。
- 前置依赖：[[M3-T3]]、[[M3-T2]]
- 完成后解锁：[[M3-T12]]

## 输入 / 产出

- **输入**：M3-T3新鲜授权、M3-T2合法登录模式和TOTP消费。
- **产出**：PATCH /api/admin/account/login-mode、POST /api/admin/account/password及同事务grant核销/审计/sv撤销。

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 调用方/接线点：两个真实handler→account-security服务
绑定本人经LOGIN_MODE grant启用后，使用下一未用验证码的真实Credentials mode=totp只提交email/totp即可登录，不含password/recoveryCode
关闭后该totp模式通用失败，password+totp仍可登录（[[E-06]]）。2) 若变更会使无已验证可用方式，409且状态不变
错误/过期/重放和两个并发同grant切换最多一个成功，最终查询仍至少一种方式
PASSWORD授权不能切换方式，原子消费/审计/递增sv使旧cookie失效（[[E-03]]、[[E-07]]、[[E-08]]、[[E-73]]）。3) 当前账号/设备在最终事务重新校验
grant5min等号、旧sv、撤销设备不变更，兼容旧currentPassword+totp路径执行同强度且非空recoveryCode拒绝（[[E-74]]）。

## 必须处理的边界

- [[E-03]]　会话持久化与记住设备期限
    - 触发：改密、重置验证器、禁用账号或执行“退出所有设备”
    - 期望：服务端撤销该账号旧凭证，旧 JWT 即使尚未到期也被拒绝；普通“退出”至少撤销当前设备会话并清除本地登录状态。
- [[E-06]]　C-03 验证器绑定与无密码默认开关
    - 触发：已绑定账号本人通过新鲜验证启用开关
    - 期望：日常登录仅要求邮箱或账号与验证器码，恢复码作为独立恢复入口，密码不再是此模式的必填项。
- [[E-07]]　C-03 验证器绑定与无密码默认开关
    - 触发：关闭无密码开关或解绑验证器会使账号失去所有可用登录方式
    - 期望：拒绝该次变更，先完成可用密码或替代方式的设置与验证，再原子提交切换。
- [[E-08]]　C-03 验证器绑定与无密码默认开关
    - 触发：绑定码错误、已过期、重复提交或并发切换
    - 期望：把四种触发分别测试，并在最终事务复核待绑定记录、有效期和当前凭证版本；错误/过期/重放不提交，两个并发切换最多一个成功，失败后查询仍存在至少一种已验证登录方式。沿09节规则，不另造登录方式。
- [[E-73]]　敏感设置的新鲜本人验证
    - 触发：两次请求并发使用同一 ActionGrant，或把改密码授权用于关闭验证器
    - 期望：在敏感变更事务内按动作、设备、账号及凭证版本校验并一次性消费授权，只有一个匹配请求成功，目的不符请求拒绝且不能执行变更。
- [[E-74]]　敏感设置的新鲜本人验证
    - 触发：授权签发后超过 5 分钟、设备撤销、密码/验证器变更或账号权限失效
    - 期望：旧授权立即无效；授权的新鲜验证不得跨设备移用，也不能延长原设备会话期限。

## 实施沉淀

<!-- notes:begin -->
- grant 按 purpose 严格分开是 E-73 的核心：`actionGrants.consume` 的 SQL 条件里 `purpose::text = 入参` 且 `"targetId" IS NULL`（LOGIN_MODE/PASSWORD 都属本人 purpose）。拿 PASSWORD grant 调 login-mode、或拿 LOGIN_MODE grant 改密码，consume 直接返回 false → `action_grant_invalid`，不会执行任何变更。消费与最终动作在同一 `db.$transaction`，并发同 grant 最多一次成功。
- User 行已由 grant 的 `consumeLocked` 在同一事务里按固定 User→Device→Grant 锁序持有 FOR UPDATE，account-repo 只读不另加锁，避免交叉死锁；最终写入用 `sessionVersion` 做 CAS，旧 sv / 设备撤销 / 5min 过期授权都不提交（E-74）。
- `consumeTotpStep` 用独立 prisma 连接做时间步核销，M3-T3 的注释明确「持着用户行锁再调它会死锁」。因此 legacy `currentPassword+totp` 路径把因子校验放在事务外，成功后再进事务；新密码等于当前密码的策略校验、当前账号复核、sv+1、撤销设备、审计都放事务内，两条路径最终强度一致。
- 非空 recoveryCode 一律拒绝：旧 password 路由的 Body 允许 `recoveryCode`，契约 `PasswordChangeRequestSchema` 的 legacy 分支把它钉成 `z.literal('').optional()`，strict 下非空直接 400 `invalid`。`login.ts:242` 那个 `TODO(M3-T19)` 的日常路径移除恢复码登录属 R5-T59021355，本任务不动。
- E-07 的判定放在最终事务里重查的 `user` 上：启用无密码但 `totpEnabled=false || totpSecret=null` 时抛 `version_conflict` 且零写入（产出不了可用的 totp 模式）。关闭无密码后 passwordHash 恒非空、password+TOTP 仍可用，不会失去所有方式。这条用 service 级 fake repo 直接测，不依赖无 TOTP 账号能否登录（那种账号本就进不了后台）。
- 旧 password 路由返回 `weak_password`/`same_password`/`locked` 等 legacy 错误码，新路由统一走 `AppError` + `classifyThrown` 的 `{error,requestId,fieldErrors?}` 信封；`AccountModeRequestSchema`/`PasswordChangeRequestSchema`/两个 DTO 都复用契约既有定义，不在路由里另造类型。密码策略错误用 `fieldErrors.newPassword` 表达，不回显旧码。
- 改密/切换成功后 sv 递增并撤销 `< 新 sv` 的旧设备，旧 JWT 即使未到期也被 guard 拒绝（E-03）；成功响应仍沿用 `PasswordChangeDTO` 的 `{ok:true, reauthRequired:true}`，不破坏前端既有消费。
- `composition.ts` 只追加 `accountSecurity` 注册、复用同一 `actionGrants`；未碰 `src/app/api/admin/account/devices/`（M3-T17 的目录）、analytics/stats/recovery 段。按分派边界，M3-T16 落地后立即接 R5-T59021355，不在此提前改 `auth.ts`/`login.ts` 的日常恢复码路径。
- 本机无 PostgreSQL，`tests/admin-account-mode-password.http.test.ts` 默认 skip，CI 用 M3T3_TEST_DATABASE_URL 专用库必跑；本机不冒充已跑 PG 并发锁证据。pnpm 11 与锁文件 overrides 不匹配，按 17 节用 npx pnpm@10.34.6 冻结安装。
