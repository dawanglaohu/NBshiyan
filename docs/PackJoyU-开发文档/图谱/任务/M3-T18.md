# M3-T18　提供受OS权限保护的本地恢复预授权CLI

- 所属模块：[[M3]]　后台访问与账号：负责统一后台登录页和后台公共外壳、个人设置、设备会话、验证器绑定与登录方式切换、会话撤销及独立受限恢复，并负责既有后台页面的共享视觉迁移/回归；不改其询盘/邮件/规格/模型业务，消费 M1 的唯一视觉 token。
- 前置依赖：[[M3-T4]]
- 完成后解锁：[[M3-T11]]、[[M7-T5]]

## 输入 / 产出

- **输入**：M3-T4同源permit持久规则与既有初始密码脚本guard/Argon参数。
- **产出**：scripts/admin-authorize-recovery.mjs；显式target/role/reason、TTY隐式密码预授权及安全审计。

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 真实CLI仅OS管理权限下针对明确target、当前role、reason签15min一次性permit
非TTY或不明目标拒绝且无记录，输出凭据一次、审计只actor/target/source/time/reason无秘密
无第二管理员且无恢复码的隔离账号取得有效permit（[[E-12]]）。2) 可选改密在TTY隐藏输入并确认，沿既有Argon规则只写pendingPasswordHash，原password/TOTP此时不变
原初始密码脚本ADMIN/未绑定/未停用/TTY guard原样，不能先清因素绕过
HTTP不得提交pendingPasswordHash（[[E-75]]）。

## 必须处理的边界

- [[E-12]]　C-04 验证器丢失与单管理员恢复
    - 触发：验证器与全部恢复码同时丢失且没有第二管理员
    - 期望：仅允许具有服务器操作系统管理权限的所有者执行本地恢复命令，为明确目标账号生成一次性凭据，记录操作者、时间和目标，不把凭据明文写入审计日志。
- [[E-75]]　敏感设置的新鲜本人验证
    - 触发：用户忘记现密码但仍能使用启用后的无密码登录
    - 期望：把“D3”指向09/10节已定义受限恢复路径和一次性 permit/restricted cookie；普通无密码登录不改，敏感设置缺当前密码时不得签发普通 ActionGrant，仅凭已登录会话或一枚TOTP的直接请求拒绝并无变更，受限恢复只可新绑定且审计。

- 实现随 PR #521 合入（实现头 `e951454f`、merge `64e37afa`，5 文件 / +1119：`admin-authorize-recovery.mjs`、`.d.mts`、`owner-recovery.ts`、`recovery-repo.ts`(+15)、`admin-owner-recovery-cli.test.ts`）。CLI 是 standalone `.mjs`，运行时不 import TS 服务层；`owner-recovery.ts` 是行为等价的 TS 服务层（含 `issue()` 事务、`decidePreflight`、`OwnerRecoveryRefusal`、`permitLines`），测试只用「源码比对 + 行为等价」钉住 `decideTarget` 一处防漂移（#414），两层 `auditMeta` 已有细微差异（CLI 多 `via`、actor 构造 `env.USER` vs `process.env.USER??USERNAME??'unknown'`），均为非秘密。属「同一契约两套实现、TS 层无产品调用方」的架构冗余/简化候选，不影响 CLI 实际安全行为，后续收口时明确其定位。
- 为什么 OS-owner 判定不降级：POSIX 刻意只认 `euid===0`、不看补充组（避免把 docker 组之类误判为管理权限），Windows 靠打开 `\\.\PHYSICALDRIVE0` 独占写，其他平台/探测缺失一律拒绝；`stdin`/`stdout` 非 TTY 在连库前 `not_tty` 返回、断言 `writes.length===0`，凭据不落文件/管道/日志。
- 「依法一次性返回」（凭据打印到交互终端一次）与「禁止日志泄露」（不进 auditLog/文件/stderr/参数）是两条独立实现且各有断言，没有把「必须返回」误做成「也禁输出」，也没把输出放进审计。`auditMeta` 固定键、stderr 只固定文案、`db_error` 只输出 `e?.name` 不带连接串；密码环境变量只删不读。
