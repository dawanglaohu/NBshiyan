# 部署与运维

本节沿用当前自托管形态，并规定本轮功能的发布准备。文档生成、恢复草稿PR和隔离验证不包含生产合并、上线、扩容、凭据轮换或业务数据删除；本节没有执行部署，也不把历史资源快照当当前容量。

## 分发形态

主要交付为仓库源码与经过审核的Linux Docker镜像、Compose及部署脚本。应用镜像运行Next standalone `server.js`，配套migrate镜像只带锁定Prisma CLI与`prisma/schema.prisma`；没有Windows/macOS安装包或新托管平台。离线交付沿`deploy/build-offbox.sh`输出`nbshiyan-images-`加12位提交SHA及`.tar.zst`后缀、SHA256校验文件及manifest，在服务器由`import-and-scan.sh`校验内容、镜像ID、平台、revision与泄漏扫描后才提升candidate。构建输入为已合入main的完整40位SHA。

随包包括standalone运行文件、`.next/static`、准许公开的`public`发布副本、现有受控管理员脚本、Prisma客户端、schema、部署及cron模板；原MP4/PDF/JPG/GIF、远程软件工程、生产配置、备份及恢复档案不进入镜像或public。站外构建不带生产秘密，只接白名单公开build args，不能把运行env文件复制进build context。

运行依赖为Linux Docker/Compose、PostgreSQL 17、现有Redis 7与Upstash兼容REST服务及内部TLS终止、宿主HTTPS反向代理，以及按配置实际使用的SMTP、Turnstile、Sanity；本轮继续local上传驱动，不新增第二数据库、消息broker或收费聊天服务。应用仅发布`127.0.0.1:3000`供既有反代访问，数据库、Redis、内部报告与health不直接公网开放。应用uid1001、只读根文件系统与受控上传挂载延续现有Compose约束。

## 环境矩阵

| 环境 | 运行与数据 | 配置/验收约束 |
|---|---|---|
| Windows开发 | 独立任务worktree、Node22/pnpm10、专用测试PG；本机端口避开现有服务 | 不使用生产连接；standalone symlink权限失败记未通过，Linux完成分发构建；主检出不切任务分支 |
| Linux CI | Node22、pnpm10冻结安装、PG17、Chromium、临时测试管理员/验证器 | 真实Next+DB+浏览器；测试域和测试key仅限隔离环境，17节适用DB/standalone检查不得因缺配置跳过算通过 |
| 隔离发布演练 | 与生产一致的candidate镜像/反代/持久存储/调度，隔离DB和SMTP接收器 | 实测schema diff/启动失败关闭/旧版兼容/重启消费/回滚/恢复；没有真实消费者数据或生产邮件收件人 |
| 生产 | 经审查的main SHA、现有受保护env与数据卷、宿主反代及cron | 实际发布另行授权；启动验证完整运行配置；新增真实清理默认关闭并dry-run，未获保留策略授权不得启用 |

正式域名、证书、反代与现有运行参数以获授权部署环境核验为准。源码模板含既有`geiom.com`示例不构成重定向域名或DNS变更授权；APP_ORIGIN、AUTH_URL、NEXT_PUBLIC_SITE_URL必须指同一受支持正式origin，不混用浏览器监听地址。

## 配置项清单

下表列名称与责任，绝不存真实值。**现存**来源为`deploy/env.template`、根`prod-env-check.ts`、`src/lib/server/startup/env-check.ts`、邮件配置及部署脚本；**新增策略**是在`src/lib/server/config.ts`内集中验证的类型化配置/常量，不表示这些字段已存在或另起同名环境变量。环境配置重启生效，站点时区等版本化设置按数据库revision生效。缺必需生产配置退出1，只报告名称/原因；构建只验证公开字段，运行由instrumentation再次验证。

## 发布与schema顺序

1. 实时核对目标main完整SHA、PR审查及同head检查，来源候选只按独立评审结果复用；安全审查阻断未解除的恢复草稿不因本规格存在而合并。先完成17节隔离链路、媒体来源/副本和旧版读取兼容验证。
2. 使用现有站内或站外构建路径，只传公开build args，固定基础镜像digest；校验manifest/SHA、运行配置泄漏扫描、资源闸门及反代secret一致性。不运行全局Docker prune，不触碰其他应用镜像/卷。
3. 保留部署前PG自定义格式备份、上传资产与当前/previous镜像、配置版本及安全哈希。备份包含新表/设置/凭证版本，真实秘密单独受保护保管；不能仅备份schema而丢聊天/会话状态。
4. **仍以schema-first部署**：`pg_dump`成功→`prisma migrate diff --script`生成当前库到`schema.prisma`的计划→现有`plan-check.sh`逐语句/子句审查→必要时精确计划哈希复核→`prisma db push --skip-generate`→`migrate diff --exit-code`为0→启动candidate→真实冒烟。没有`prisma/migrations`，`prisma/sql/*.sql`不打入migrate镜像且不执行；不得加`--accept-data-loss`、手工DDL或改闸门来强行继续。
5. 先部署新增表及有default/nullable列，幂等创建新设置与默认关闭的功能；设备会话不从旧JWT回填，现有管理员重新登录。首次开启无密码由本人完成验证开关，不能批量替账号启用。约束、唯一索引与现存表变更触发审查时按实际计划处理，不能把“新增模型”当无风险通行证。
6. 启动检查必须真实失败关闭；APP_ENV构建/运行一致、生产key及权限/TLS正确。内部health只验证DB连通，随后额外验证首页样式、实际登录/受保护接口、聊天保存/回复、同意与事件、计划聚合/看板及来源状态。看板只读刷新不替代后台作业。
7. 安装并核对下节cron；重启后等真实计划完成并核JobState与安全计数。功能所属任务随交付接线，不等最终M7补基础。正式开启新增真实清理前需另有明确生产保留授权；其余功能可以在dry-run下验收候选集合和可用性，界面明确清理未启用。

## 固定作业与cron

现有`deploy/cron.nbshiyan`仅含每日03:00上传清理与04:30备份；已有mail-queue API不等于模板已调度。本轮保持原计划与既有授权范围，追加下表实际注册。cron按服务器本地时区触发，统计自然日始终取SiteSetting时区。

| key/既有任务 | 所属实现与组合点 | 生产计划与验收 |
|---|---|---|
| analytics-aggregate | M5 `jobs/registry.ts`基础与`server/composition.ts`生产注册；POST operations固定jobKey | 每5分钟；真实事件→事务替换→成功watermark，重启仍计划运行；重叠返回busy且不覆盖新代次 |
| analytics-retention | M5分析保留服务；同operations入口 | 每日；默认dry-run/真实清理关闭，报告候选与0删除，另授权才可启用；不碰备份 |
| chat-notifications | M4专属持久出箱，复用安全SMTP适配器 | 每分钟；保存后进程中断仍能消费，稳定Message-ID与至少一次有界重试；保存/通知结果独立 |
| chat-retention | M4聊天策略/并发重查 | 每日；默认dry-run/关闭真实清理，咨询并发推进截止后跳过，既有询盘策略不变 |
| mail-queue | M4补既有POST `/api/admin/cron/mail-queue`调度及JobState摘要 | 每分钟，仍先既有邮件gate；无配置/关闭不能报成功。GET别名保兼容但不作浏览器导航/预取/自动重试 |
| ops-sample | M6固定受控脚本/采样服务及POST `/api/internal/ops-report` | 每15分钟；只采bytes/真实备份完成及验证元数据，按source+measuredAt单调提交，不能上传文件内容/任意路径 |
| cleanup-uploads / backup | 既有部署脚本，不扩大范围 | 保留原03:00/04:30及其既有策略；新增功能不获得删除恢复目录/原附件权限 |

`CRON_SECRET`从运行容器环境读取，不放命令行字面值、浏览器或cron日志；保持受控本机路径、请求截止与退出码。固定operations入口不接受任意代码/路径/job名，HTTP客户端不自动重试副作用触发，超时后只读JobState/队列状态核实，留下一计划按持久状态恢复。不得以setInterval、Next after()、页面GET副作用或仅手调API代替持久作业。

## 回滚、备份与恢复

现有`deploy.sh rollback`只切previous应用镜像，不回滚schema。新增列/表必须先证明旧应用可读且不破坏安全状态；发布后不能为兼容旧应用回退User.sv、恢复已核销码或复活设备。若previous缺设备会话/新撤销校验，后台入口保持维护/拒绝并选择已经兼容的安全版本，不能以可登录为由恢复弱鉴权。schema不兼容或数据已变更时停止自动回退，提交后端专门审查的恢复计划。

既有备份脚本生成PG `-Fc`，`pg_restore --list`确认档案可读，采用7日/4周/最多3份部署前档的现行策略并有容量告警；这是当前源码行为，不授权本轮运行其轮换删除或改变保护备份保留期。需要试验时只在隔离备份目录，禁止对恢复档案、原始媒体或其他项目执行轮换。目录备份与密钥备份分开权限保护，日志/截图不含内容和连接信息。

可恢复验收必须把备份恢复到一次性数据库，核schema、行数/约束和真实应用读取/登录流程，不能用`--list`或“文件存在”宣称恢复成功。恢复可能包含旧sv或已撤销凭据，切回提供服务前应按受控流程使恢复前会话/permit/grant失效并重新登录，不能重新接受已用一次性材料；具体恢复操作及生产数据覆盖另授权。

看板备份状态只接受真实完成/验证时间和安全结果；未接入显示未接入，未做恢复验证不得标为可恢复。运行手册记录精确SHA、镜像ID、计划哈希、配置版本、最近备份/恢复演练与调度结果；健康、队列、存储和邮件失败按16节各自来源排查，不用看板查询时间伪造采集心跳。

## 代理验收的构建工作区

现有build-offbox.sh内部会mktemp并git clone；代理任务不得直接执行这一包装去绕过AGENTS的两个目录纪律。M7-T9在本任务既有worktree确认合入main的完整SHA，再用git archive把受控源码导出到任务planning目录内build-source；宿主不新增clone。按现有脚本已审核的Dockerfile/BuildKit固定版本、公开build-args白名单、revision/buildarg标签、runner+migrate构建、镜像检查、打包manifest/SHA和import-and-scan子步骤执行等价隔离验收，逐条记录实际命令与结果，不能省略泄漏/平台/版本校验。schema与备份恢复只用一次性PG和隔离挂载，结果元数据对应真实操作；不改变分发形式、原反代/部署平台、生产配置或删除授权。此执行位置限定用于代理验收，不授权发布。
